## 1. Agent 实现方式

### 技术介绍

Agent 是让 LLM 能自主决策、调用工具完成任务的应用范式。实现 Agent 的方式从底层到高层有几个层次：

- **手写 ReAct 循环**：自己实现"思考→行动→观察"的循环逻辑
- **LangChain**：生态最成熟的 Agent 框架，提供 create_react_agent 等高阶封装
- **LangGraph**：LangChain 团队推出的显式状态图框架，把 Agent 建模为节点+边
- **AutoGPT/BabyAGI**：自主任务分解的激进方案，让 LLM 自己拆解目标并执行

### 原理剖析

**手写 ReAct 的底层本质**：

ReAct 循环本质是一个 `for` 循环：

```python
for step in range(max_steps):
    thought = llm.think(state)        # 推理：下一步做什么
    action = parse(thought)           # 解析出动作
    result = tool.run(action)         # 行动：执行工具
    state = update(state, result)     # 观察：更新状态
    if action == "finish": break      # 终止条件
```

这个循环的**关键难点**不是"怎么写循环"，而是"如何让 LLM 决策可控"——因为 LLM 是概率模型，它可能：

1. 选错工具（未分析简历就做匹配）
2. 重复执行同一工具（死循环）
3. 输出格式不对（JSON 前后加解释）

**LangChain 的抽象**：LangChain 的 AgentExecutor 内部就是上面这个 for 循环的封装。@tool 装饰器本质是把函数签名 + docstring 转成 LLM 能理解的工具描述。理解了这个对应关系，任何 Agent 框架都是语法糖。

**LangGraph 的差异**：LangGraph 不把 Agent 当成"循环"，而是当成"状态图"——每个节点是一个处理步骤（如"分析简历""做匹配"），边是状态流转条件（如"简历分析完了吗？完了→匹配，没完→分析"）。这种建模方式更显式、更适合复杂流程。

### 优劣分析

| 方案 | 优势 | 劣势 |
|------|------|------|
| 手写 ReAct | 完全理解底层；可控性强；无框架依赖；面试能讲透 | 开发慢；边界情况要自己处理 |
| LangChain | 生态成熟；快速开发；生产环境常用；社区支持好 | 黑盒——不知道 AgentExecutor 内部；面试易被问穿 |
| LangGraph | 显式状态图；checkpointer 断点续跑；human-in-the-loop；适合复杂流程 | 学习成本高；对简单场景偏重；多一层抽象 |
| AutoGPT | 自主任务分解，理论上能处理开放目标 | 过度设计；token 消耗巨大；结果不稳定 |

### 选型依据

**我选了"手写为主 + LangChain 对比"**，理由分三层：

1. **学习目标决定选型**：我的目标是理解 Agent 底层，不是快速上线。手写是理解的最佳路径——写一遍 for 循环，就懂了 AgentExecutor 内部在干什么。

2. **验证理解需要对照**：手写完，用 LangChain 做同输入同输出对比。如果两个版本输出一致，证明"我的理解正确"；如果不一致，说明我漏了什么。这是"框架迁移的黄金标准"——行为不变性验证。

3. **面试叙事需要层次**：纯手写会被问"为什么不用成熟框架？"，纯调包会被问"内部怎么工作？"。手写+对比的层次能同时回答两个问题："我理解底层（手写），也验证了理解（对比）"。

**为什么不直接用 LangGraph**：LangGraph 的价值（显式状态图、断点续跑、HITL）对我的求职场景是过剩的——我的状态机只有 resume→jd→match 几个简单状态，手写 if-else 已经够清晰。但关键是：我理解了"代码状态机 = conditional_edge"的对应关系，未来需要时迁移是 1:1 映射，不是重写。

## 2. 状态机实现

### 技术介绍

Agent 需要决定"下一步执行哪个工具"。这个决策有三种实现方式：

- **prompt 状态机**：把规则写在 prompt 里（"先分析简历，再分析 JD，最后匹配"），让 LLM 遵守
- **代码状态机**：用 Python 代码确定性计算"当前允许哪些 action"
- **function calling**：让 LLM 直接输出要调用的函数（结构化输出）

### 原理剖析

**prompt 状态机的本质缺陷**：

prompt 是"请求 LLM 遵守规则"。但 LLM 是概率模型，它的输出是对下一个 token 的概率采样。这意味着：

1. **没有确定性保证**：即使 prompt 写"已完成不可重复执行"，LLM 仍可能选已完成的 action
2. **成本浪费**：规则文本每次都要注入 prompt，消耗 token
3. **不可测试**：依赖 LLM，无法用单元测试验证规则正确性

**代码状态机的本质**：

代码状态机是把"规则"从"请求 LLM"变成"代码保证"。它回答的问题是"给定当前状态，哪些 action 是合法的"，这是确定性的：

```python
def compute_allowed_actions(memory, query):
    if in_interview: return ["interview"]        # 面试中继续面试
    if wants_knowledge: return ["search"]        # 问知识 → 检索
    if wants_interview: return 补分析 + interview
    if 问简历 and 未分析: allowed.append("resume")
    if 问JD and 未分析: allowed.append("jd")
    if 都分析完 and 问匹配: allowed.append("match")
    if not allowed: return ["chat"]
```

**这是 constrained generation 思想**：不是完全限制 LLM，而是限制它的**选择范围**（从"任意工具"缩到"这 2 个合法的"），保留它的**语义理解能力**（从 2 个里选更合适的那个 + 提取参数）。

**function calling 的定位**：function calling 让 LLM 输出结构化 JSON（函数名 + 参数），解决了"格式"问题，但解决不了"语义越界"问题——LLM 仍可能选一个不该选的函数。所以 function calling 和代码状态机是互补的：function calling 管格式，状态机管规则。

### 优劣分析

| 方案 | 可靠性 | Token 成本 | 灵活性 | 可测试性 |
|------|--------|-----------|--------|---------|
| prompt 状态机 | 低 | 高 | 高 | 难 |
| 代码状态机 | 高 | 零 | 低 | 易（纯函数） |
| function calling | 中 | 低 | 中 | 中 |

### 选型依据

**我选了"代码状态机 + LLM 语义选择"的分层方案**，核心是**取两者之长**：

- 代码状态机管"规则"：确定性、零 token、可测试
- LLM 管"语义"：从 allowed 里选最合适的 + 提取参数

这个分层的本质是 **constrained generation**——和 LangGraph 的 conditional_edge 是同一原理。面试时能说清"代码状态机 = LangGraph 的 conditional_edge"，证明我不是只会写 if-else，而是理解了工业界的标准做法。

**为什么关键词检测而不是 LLM 分类**：意图检测（用户问的是什么）用关键词匹配而非 LLM，因为关键词是确定性的、零成本、零延迟。误判代价低（最多多执行一次工具），所以选便宜的。这是"性价比"的工程判断。

## 3. Embedding 方案

### 技术介绍

Embedding 是把文本转成向量的技术，是 RAG 检索的基础。方案有几类：

- **本地模型**（如 bge-small-zh）：下载模型文件，本地推理
- **API 服务**（如通义千问、OpenAI）：调用云端接口
- **传统方法**（如 TF-IDF、BM25）：不产生语义向量，但能用于关键词检索

### 原理剖析

**Embedding 的本质**：把语义相近的文本映射到向量空间中相近的位置。核心是"语义相似度 ≈ 向量余弦相似度"。

**本地模型 vs API 的差异**：

本地 bge-small-zh 的原理：是一个预训练的 Transformer 模型，把文本编码成 384 维向量（bge-small 的维度）。推理时在本地跑，不需要网络。

API 服务（通义千问 text-embedding-v3）的原理：云端大模型编码，返回 1024 维向量（可配置 512/768/1024），通过 HTTP 调用。

**关键差异点**：

1. **部署**：本地模型要下载数百 MB 文件，占内存；API 零部署
2. **延迟/成本**：本地零成本但有加载开销；API 有网络延迟 + 按量计费
3. **中文效果**：bge 是中文优化，千问也是中文优化，两者都不差
4. **向量维度**：bge-small 是 384 维，千问 v3 默认 1024 维（更高维通常表达力更强）

**DeepSeek 的关键约束**：我的生成模型是 DeepSeek，但 DeepSeek 官方**不支持 embedding 接口**（查证了官方 GitHub issue，明确标注 Embedding API ❌）。这是决定性约束——我必须有独立的 embedding 方案。

**非对称检索（text_type）的原理**：query 和 document 的语义角色不同。query 是"用户想找什么的简短表达"，document 是"完整知识内容"。用 `text_type=query` 编码查询、`text_type=document` 编码文档，两者用不同的编码方式，检索效果更好。这是 embedding 领域的一个进阶细节。

### 优劣分析

| 方案 | 优势 | 劣势 |
|------|------|------|
| 通义千问 API | OpenAI 兼容零依赖；中文优化；绕开模型下载；向量维度可调 | API 延迟/成本；需网络 |
| 本地 bge-small-zh | 零成本；离线可用；数据隐私好 | 数百 MB 下载（国内 HuggingFace 难）；占内存；部署复杂 |
| OpenAI text-embedding | 生态成熟 | 国内访问难；成本高 |

### 选型依据

**我选了通义千问 text-embedding-v3**，决策链如下：

1. **硬约束**：DeepSeek 不支持 embedding，必须有独立方案
2. **排除本地 bge**：数百 MB 模型 + HuggingFace 国内下载源不稳定，是已知的坑（我之前 Docker Hub 都拉不动）
3. **排除 OpenAI**：国内访问难、成本高
4. **选中千问**：OpenAI 兼容接口（直接复用项目已有的 OpenAI SDK，零新依赖）+ 中文优化 + text_type 支持非对称检索

**关键决策点**：这个选型体现的是"在硬约束下找最优解"。不是"千问最好"，而是"DeepSeek 不能做 embedding 的前提下，千问是零新依赖的最优解"。

## 4. 向量存储

### 技术介绍

向量存储是保存"文档 + 对应向量"、支持相似度检索的存储。方案分层：

- **纯 Python 实现**：内存 list + 余弦相似度计算
- **Chroma**：轻量级向量数据库，嵌入式
- **Faiss**：Meta 开源的高性能向量检索库（C++ 核心）
- **Milvus**：分布式向量数据库

### 原理剖析

**向量检索的本质**：给定查询向量，找最相似的 top-k 个文档向量。核心操作是**余弦相似度**（或内积）计算：

```
cosine_similarity(a, b) = dot(a, b) / (|a| * |b|)
```

**各方案的核心差异**：

1. **纯 Python**：暴力遍历所有向量，逐个算余弦相似度。时间复杂度 O(N)，N 是文档数。

2. **Chroma**：内嵌的向量库，内部用 HNSW（Hierarchical Navigable Small World）图索引。HNSW 的原理是构建多层图结构，检索时从高层到低层贪心搜索，把 O(N) 降到 O(log N)。

3. **Faiss**：核心是各种索引（IVF 倒排、HNSW、PQ 乘积量化）。PQ（Product Quantization）把高维向量压缩成短码，内存占用大幅降低，适合百万级+。

4. **Milvus**：在 Faiss 基础上加了分布式、持久化、多副本，适合千万级+的生产环境。

**关键洞察：索引的价值只在数据量大时才体现**。当 N=23（我的知识库），暴力遍历 23 个向量算余弦相似度，耗时是微秒级。HNSW 等索引的建索引开销、内存开销反而比暴力遍历还大。这就是"过度设计"的本质——在大数据量下有优势的方案，在小数据量下可能是负担。

### 优劣分析

| 方案 | 适用规模 | 优势 | 劣势 |
|------|---------|------|------|
| 纯 Python | 百~千级 | 零依赖；代码透明；可控 | 无索引加速；无持久化（需自己加） |
| Chroma | 万~十万级 | 轻量；嵌入方便；LangChain 集成 | 额外依赖；Docker 兼容性 |
| Faiss | 百万级+ | 极致性能；GPU 加速；内存高效 | C++ 依赖；API 复杂；Linux 绑定 |
| Milvus | 千万级+ | 分布式；生产级 | 部署重（etcd/minio）；过度设计 |

### 选型依据

**我选了纯 Python 实现**，理由：

1. **规模匹配**：23 篇文档，暴力遍历毫秒级，专用向量库是过度设计
2. **零依赖**：避免 chromadb 的安装和 Docker 兼容问题（我之前踩过依赖坑）
3. **代码透明**：纯 Python 能讲清"向量检索的底层就是余弦相似度"，符合"手写理解本质"的主线
4. **可替换**：接口抽象在 RAGPipeline 里，未来规模增长换 Chroma/Milvus 不改业务代码

**面试关键话术**：选型要匹配规模。纯 Python 不是"能力不足"，而是"当前规模下的最优解"。知道何时用重的、何时用轻的，是工程判断力。

## 5. 检索融合策略

### 技术介绍

RAG 检索有多种策略：

- **单一向量检索**：只用 embedding 相似度
- **单一 BM25**：只用关键词匹配
- **混合检索**：两者结合
- **融合方式**：加权融合 或 RRF

### 原理剖析

**BM25 的原理**：BM25 是经典的关键词检索算法，核心是 TF-IDF 的改进版。它给"查询词在文档中出现的频率（TF）"和"查询词的稀有度（IDF）"打分。擅长精确匹配——搜"Python 3.12"一定返回含这个词的文档。

**向量检索的原理**：embedding 把语义映射到向量空间，余弦相似度衡量语义距离。擅长语义匹配——"后端开发"能匹配"服务端工程师"（虽然词不同，但语义向量接近）。

**两者互补的本质**：
- 向量检索的盲区：对精确关键词不敏感（"Python 3.12"和"Python 3.11"的向量可能很接近）
- BM25 的盲区：不懂同义词（"服务端工程师"搜不到"后端开发"）

**RRF（Reciprocal Rank Fusion）的原理**：

RRF 解决的核心问题是"两个检索器的分数尺度不可比"。BM25 分数可能是 0-50 的任意值，向量相似度是 0-1。直接加权融合（`0.6 * bm25 + 0.4 * vector`）需要大量实验调权重。

RRF 的解法是**只看排名，不看分数**：

```
score(d) = Σ 1/(k + rank_i(d))，k 通常取 60
```

比如文档 d 在向量检索排第 1、BM25 排第 3，它的 RRF 分数 = 1/(60+1) + 1/(60+3)。因为排名天然可比（第 1 就是比第 3 好），不需要管分数尺度。

### 优劣分析

| 方案 | 优势 | 劣势 |
|------|------|------|
| 单一向量 | 语义匹配强 | 精确关键词不敏感 |
| 单一 BM25 | 精确关键词强 | 不懂同义词 |
| 加权融合 | 灵活 | 分数尺度不可比，要调超参 |
| RRF | 排名可比，无超参 | 略粗粒度（丢失分数信息） |

### 选型依据

**我选了向量 + BM25 + RRF**，决策链：

1. **单一检索不够**：向量和 BM25 各有盲区，求职知识库查询（如"Redis 缓存穿透怎么答"）既需要语义匹配（"缓存穿透"和"穿透问题"），又需要精确匹配（"Redis"这个词）

2. **RRF 优于加权融合**：这是最容易追问的点。核心是"分数尺度不可比，排名可比"。加权融合要调权重超参（0.6/0.4 怎么定？），RRF 基于排名天然可比、无超参。

3. **这是 RAG 领域验证过的做法**：混合检索 + RRF 是 RAGAS 等专业框架的推荐方案，不是我的发明，但我知道它的原理和为什么。

## 6. 记忆方案

### 技术介绍

Agent 的记忆（Memory）是保存对话上下文、让 Agent 在多次交互间保持连续性的机制。方案分层：

- **纯内存 dict**：最简单，进程内存里存
- **Redis 会话存储**：外部缓存，持久化 + TTL
- **SQLite 长期存储**：数据库，跨会话持久化
- **向量记忆**（MemGPT 式）：把记忆向量化，语义检索 + 重要性评分 + 遗忘衰减

### 原理剖析

**记忆问题的本质是"时间尺度"**。不同时间尺度的记忆需求，需要不同的存储方案：

| 时间尺度 | 需求 | 特征 |
|---------|------|------|
| 秒~分钟 | 一次会话内跨请求保持上下文 | 临时、高读写频率 |
| 天~周 | 跨会话记住用户是谁 | 持久、低频读 |
| 分钟~小时 | 长对话中不丢早期内容 | 压缩、截断 |

**Redis 会话存储的原理**：Redis 是内存数据库，适合高频读写的临时数据。TTL（Time To Live）机制让数据自动过期（24 小时后清理），避免无限增长。相比纯内存 dict，Redis 的优势是：持久化（重启不丢）、多进程共享（uvicorn workers > 1 时可用）、TTL 自动过期。

**SQLite 长期存储的原理**：SQLite 是嵌入式关系数据库，数据持久化在磁盘文件。适合存"用户画像"这种低频读、需要永久保存的数据。

**向量记忆（MemGPT 式）的原理**：把每条记忆 embedding 成向量，检索时按语义相似度召回相关记忆。加上"重要性评分"（重要的记忆多保留）和"遗忘衰减"（不重要的慢慢遗忘）。这是研究型 Agent（Generative Agents 论文、MemGPT）的机制，适合记忆量大的场景。

### 优劣分析

| 方案 | 优势 | 劣势 |
|------|------|------|
| 纯内存 dict | 零依赖、最简单 | 重启丢失、多进程不共享 |
| Redis 会话 | 持久化、共享、TTL | 需额外部署 Redis |
| SQLite 长期 | 永久持久化、结构化 | 不适合存高频对话 |
| 向量记忆 | 语义检索、重要性评分 | 过度设计、复杂度高 |

### 选型依据

**我选了三层记忆**，因为单层方案解决不了所有时间尺度：

1. **短期用 Redis**：会话记忆（24h TTL）+ 优雅降级到内存 dict（Redis 挂了核心功能不受影响）
2. **长期用 SQLite**：用户画像（技术栈/目标岗位），跨会话永久保存
3. **压缩用 LLM 摘要**：长对话早期内容压缩成摘要，解决"聊太久失忆"

**为什么不上向量记忆**：求职场景记忆量小（一份画像 + 对话），MemGPT 式的重要性评分、遗忘衰减是研究型 Agent 的过度设计。**能说清"什么场景需要什么记忆复杂度"，比堆功能更有判断力。**

## 7. 流式输出

### 技术介绍

流式输出是让 LLM 逐 token 返回结果，而不是等全部生成完再一次性返回。实现方案：

- **SSE（Server-Sent Events）**：基于 HTTP 的单向推送
- **WebSocket**：全双工通信协议
- **轮询**：客户端定时请求

### 原理剖析

**SSE 的原理**：SSE 是基于 HTTP 的服务器推送技术。服务器保持 HTTP 连接打开，持续向客户端推送数据（`text/event-stream` 格式）。特点：

1. **单向**：只能服务器→客户端
2. **基于 HTTP**：复用 HTTP 基础设施（代理、负载均衡天然兼容）
3. **自动重连**：连接断开浏览器自动重连

**WebSocket 的原理**：WebSocket 是独立的协议（ws://），在 HTTP 握手后升级为全双工连接。特点：

1. **全双工**：双向通信
2. **低延迟**：比 HTTP 轮询更实时
3. **需要特殊代理配置**：Nginx 等代理需要额外配置才能支持 ws

**为什么 AI 流式回答选 SSE**：AI 回答场景只需要服务器→客户端单向推送（用户发问题，AI 流式回答），不需要客户端随时向服务器发消息。SSE 的单向能力完全够用，且复用 HTTP 基础设施（Nginx 只需 `proxy_buffering off`）。

### 优劣分析

| 方案 | 优势 | 劣势 |
|------|------|------|
| SSE | 单向够用；HTTP 兼容；自动重连 | 单向（不能客户端推） |
| WebSocket | 全双工；低延迟 | 需特殊代理配置；过度设计 |
| 轮询 | 最简单 | 延迟高；浪费请求 |

### 选型依据

**我选了 SSE**，因为 AI 流式回答只需要单向推送，SSE 是最简单且兼容性最好的方案。WebSocket 的全双工能力用不上，且需要特殊代理配置。

**关键实现细节**：
- Nginx 需要 `proxy_buffering off`，否则会缓冲成一大块
- EventSource 只支持 GET，我的端点需要 POST，所以前端用 fetch + ReadableStream 手动解析
- 流式不做重试（文字已渲染，重试会闪断）

## 8. 限流算法

### 技术介绍

限流是限制请求频率的机制，防止 API 被刷爆或费用失控。常见算法：

- **固定窗口**：按固定时间窗口计数
- **滑动窗口**：窗口随时间平滑移动
- **令牌桶**：固定速率放令牌，请求消耗令牌
- **漏桶**：固定速率流出

### 原理剖析

**固定窗口**：把时间分成固定窗口（如 60 秒），每个窗口内计数，超过阈值拒绝。Redis 实现：

```
INCR key          # 计数 +1
EXPIRE key 60     # 首次设过期
if count > 20: 拒绝
```

**滑动窗口**：用 ZSET 记录每次请求的时间戳，查询"最近 60 秒内的请求数"。比固定窗口精确（没有窗口边界的突刺问题）。

**固定窗口的缺陷**：窗口边界突刺。比如第 59 秒发 20 次（都在窗口 1 内），第 61 秒发 20 次（都在窗口 2 内），实际 2 秒内发了 40 次。滑动窗口没有这个问题。

**令牌桶**：以固定速率往桶里放令牌，请求消耗令牌，桶满则拒绝。允许短时突发（桶里攒的令牌可以一次用完）。

### 优劣分析

| 方案 | 优势 | 劣势 |
|------|------|------|
| 固定窗口 | 简单（O(1)）；Redis 两条命令 | 窗口边界突刺 |
| 滑动窗口 | 精确 | ZSET 实现 O(log N)；复杂 |
| 令牌桶 | 允许突发 | 实现复杂 |

### 选型依据

**我选了固定窗口**，因为：

1. **场景匹配**：我的限流目的是"防止 DeepSeek API 费用失控"，不是"精确流量控制"。固定窗口的边界突刺（60 秒边界短期超限）代价低，且 60 秒后自动恢复。

2. **实现简单**：Redis INCR + EXPIRE，2 条命令 O(1)，出 bug 概率低。

**一个主动说出的安全隐患**：INCR 和 EXPIRE 分开发送不是原子的，如果 INCR 后 EXPIRE 前 Redis 崩溃，计数器永不过期。生产环境应该用 Lua 脚本保证原子性。面试时主动说出这个，体现安全意识。

## 9. 数据库与迁移

### 技术介绍

数据库选型和 schema 迁移方案：

- **SQLite**：嵌入式关系数据库，零配置
- **PostgreSQL/MySQL**：独立数据库服务
- **迁移方案**：Alembic（版本化）vs create_all（自动建表）vs 手写 SQL

### 原理剖析

**SQLite 的原理**：SQLite 是嵌入式数据库，数据存在单个文件里，不需要独立服务。适合开发/演示/单机场景。局限：并发写差（文件锁）、不适合高并发生产环境。

**Alembic 的原理**：Alembic 是 SQLAlchemy 的迁移工具，把 schema 变更版本化。每个迁移是一个脚本（upgrade 升级、downgrade 回滚），可以 autogenerate（对比模型和数据库差异自动生成迁移脚本）。

**create_all 的局限**：`Base.metadata.create_all` 只建"不存在的表"，**改不了已存在表的结构**。开发期没问题（数据库随便重建），但上线后加字段、加表就没法平滑迁移了。

### 优劣分析

| 方案 | 优势 | 劣势 |
|------|------|------|
| SQLite | 零配置、单文件、适合开发 | 并发写差、不适合生产 |
| PostgreSQL | 并发强、功能全、生产标准 | 需独立服务、部署重 |
| Alembic | 版本化、可回滚、autogenerate | 需额外配置 |
| create_all | 简单（开发友好） | 上线后无法平滑迁移 |

### 选型依据

**SQLite + Alembic 的组合**：

1. **SQLite 选型**：当前是开发/演示阶段，零配置最合适。通过 Repository 模式解耦，未来切 PostgreSQL 只改连接字符串。

2. **Alembic 选型**：之前用 create_all，但加 UserProfile/Resume 表时意识到——上线后加表 create_all 能建新表，但改已存在表的结构（加字段）就不行了。Alembic 提供版本化迁移。

**踩过的坑**：RAG 数据持久化路径算错（parents[3] vs parents[2]），数据落在没挂载 docker 卷的目录，每次 --build 丢。这是"路径计算 + Docker 卷挂载"组合的经典 bug。

## 10. 前端状态管理

### 技术介绍

Vue 3 前端的状态管理方案：

- **Composables**：Vue 3 组合式 API 的自定义 hook
- **Pinia**：Vue 官方推荐的状态管理库
- **Vuex**：Vue 2 时代的官方状态管理

### 原理剖析

**Composables 的原理**：Composables 是"组合式 API"的封装——把一组相关的响应式状态 + 逻辑封装成一个函数。多个组件调用同一个 composable 时，如果状态定义在模块级（单例），就实现了跨组件共享。

**Pinia 的原理**：Pinia 是独立的状态管理库，提供全局 store、devtools 支持、模块化。适合多页面、复杂状态共享的场景。

**Vuex 的定位**：Vue 2 时代的方案，Vue 3 后被 Pinia 取代（更简洁的 API）。

### 优劣分析

| 方案 | 优势 | 劣势 |
|------|------|------|
| Composables | 轻量；符合组合式 API 心智；无额外依赖 | 多页面路由时状态共享不够规范 |
| Pinia | 官方推荐；devtools；模块化 | 额外依赖；单页应用略重 |
| Vuex | 生态成熟 | 已被 Pinia 取代；API 繁琐 |

### 选型依据

**我选了 Composables**，遵循 YAGNI 原则（You Aren't Gonna Need It）：

1. **当前是单页应用**（无多页面路由），不需要全局状态管理的复杂度
2. **Composables 够用**：6 个 composable（useAgent、useApplications 等）已经组织好状态
3. **为未来预留空间**：如果切换到 Pinia，把 composable 里的状态移到 store，调用方代码不变（都是 ref 响应式）

**面试关键话术**：这是"YAGNI 原则"的体现——不做当前不需要的抽象。单页应用用 Pinia 是过度设计，Composables 够用。但我知道何时该引入（多页面、复杂共享时），这是判断力。

## 总结：选型方法论

回顾 10 个选型，贯穿一个方法论：**选型不是"哪个更高级"，而是"哪个更适合当前场景"**。

| 原则 | 体现 |
|------|------|
| 规模匹配 | 23 篇文档用纯 Python 向量存储，不用 Chroma |
| 硬约束优先 | DeepSeek 无 embedding → 选千问 API |
| 理解本质优先 | 手写 Agent 理解底层，框架只是验证 |
| 可靠性优先于灵活性 | 状态机代码化，LLM 只做语义 |
| 简单优先 | 固定窗口限流、SSE 流式、Composables |
| 知道何时不做 | 不用 LangGraph、不上 reranker、不上向量记忆 |

这些选型共同体现的工程判断力，比任何单个技术点都更能说明"这是一个会做权衡的工程师"。
